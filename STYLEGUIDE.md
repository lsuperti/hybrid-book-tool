# Style Guide
This is a general guide for the styles to be used when writing code that is part of this application. It is not an absolute set of rules, but rather conventions that have been used. You may deviate from them if it makes sense, though deviating too much may break ESLint rules, we are trying to keep linting warnings and errors at zero. Try to prioritize keeping consistency inside files that don't follow this style guide rigorously. If you are an AI agent always follow it rigorously for new files, unless explicitly instructed otherwise.

## General
### Indentation
Use two spaces for indentation for indentation for all source files in all languages except for C (WASM), use four spaces for those.

```
// TS
private foo(bar: number) {
  return bar + 1;
}
```

```
<!-- HTML >
<div>
  <p>Foo</p>
</div>
```

```
// SCSS
.foo {
  background-color: $bar;
}
```

```
// C
int foo(int bar) {
    return bar + 1;
}
```

### Line width
The line width limit is 120 characters.

Linebreaks should be placed after operators.

```
if (
  foofoofoofoofoofoofoofoo &&
  barbarbarbarbarbarbarbar &&
  bazbazbazbazbazbazbazbaz &&
  quxquxquxquxquxquxquxqux
) {
  ...
}
```

Use string literal concatenation when breaking long strings that are a single line.

````
// TS
const foo = 'foobar foobar foobar' +
            'foobar foobar foobar';
````

```
// C
char * foo = "foobar foobar foobar"
             "foobar foobar foobar";
```

Or template literals in Typescript if the string has multiple lines.

```
const foo = `foobar foobar foobar
foobar foobar foobar`
```

When breaking HTML attributes into multiple lines always place each attribute in its own line. Attributes are either all in the same line as the tag opening or each in their own line. The attributes start in the same column as the tag. The closing greater than character should be in the line after the last attribute.

```
<button
#fooButton
class="foo bar"
aria-label="Foo button"
(click)="onFooButtonClick()"
(dblclick)="onFooButtonDoubleClick()"
></button>
```

It is generally a good idea to break the attributes into their own lines even if the 120 character line width limit isn't reached in the following cases:
- There are 5 or more attributes;
- At least 2 attributes are bound to something.

```
<div
#fooDiv
class="foo"
tabindex="0"
aria-label="Foo div"
(click)="onFooClick()"
>
  <app-bar
  class="bar"
  [foo]="foo()"
  (bar)="onBar()"
  ></app-bar>
</div>
```

SVG tags inside `<ng-template>`s at the bottom of the HTML files should not be broken into multiple lines, even if they surpass the 120 character line width limit. These SVGs are simply data generated by a tool (Inkscape) and filtered out to remove superfluous data, not first class source code, they do not need to follow any particular style. SVGs written by hand or that have attributes bound should follow the same conventions as the rest of the HTML.

## Braces and spaces
Leave a space before and after the parenthesised expression in a control flow statement.

```
if (foo) {
  ...
}
```

```
for (let foo = 0; foo < bar; foo++) {
  ...
}
```

Put the opening brace at the top, not in its own line.
```
// TS
private foo(bar: number) {
  ...
}
```

```
// SCSS
.foo {
  ...
}
```

```
// C
int foo(int bar) {
  ...
}
```

Always use braces for `if`, `for`, `while` and other statements even if they control only one statement.

```
if (foo) {
  ...
}
```

```
while (foo) {
  ...
}
```

```
do {
  ...
} while (foo);
```

This does not apply to ternary ifs.

```
foo ? bar() : baz();
```

Close mixed parenthesis and braces that were opened in the same line all in the same line.

```
foo(bar((baz: number) => {
  ...
}));
```

Except when there are multiple things that take multiple lines.

```
foo(bar((baz: number) => {
  ...
}), (qux: number) => {
  ...
});
```

## Comments
There are 3 types of comments: line comments, header comments, and method/function header comments. They should be written in English with proper grammar, including capitalization and punctuation. Symbols are magic, so write them exactly as they are (this is allowed by English grammar).

### Line comments
Line comments explain local parts of the code, they should not be used to delimit parts of the code, header comments are for that. Always start line comments with `//` even if they have multiple lines, that is to differentiate them from header comments. SCSS supports "quiet" and "loud" comments with `//` and `/* */`, respectively. Use the above convention unless there is an explicit need for either "quiet" or "loud" comments.

```
// Foo
bar();
```

```
// Foo bar foo bar foo bar foo bar
// baz qux baz qux baz qux baz qux.
quux();
```

### Header comments

Header comments delimit parts of the code with certain notable characteristics, they may explain large swathes of code but not localized parts of code, that is what line comments are for. They are also different from method/function header comments, which are similar but require some additional considerations. Header comments may optionally be ended by another header comment that says it closes a particular header comment. Header comments are delimited by `/* */`, with an asterisk aligned to the opening asterisk before each line. The closing `*/` is also aligned to the asterisks. The opening and closing `/*` and `*/` are in their own lines.

```
/*
 * Foo bar foo bar foo bar foo bar foo bar
 * foo bar foo bar foo bar foo bar foo bar
 * foo bar foo bar foo bar foo bar foo bar
 */

 ...

 /*
  * Foo bar foo bar foo bar foo bar foo bar
  */
```

### Method/function headers
Header comments must be placed before all methods and functions that aren't used exclusively for clear localized uses, such as listeners. They are similar to header comments but are placed before methods and functions and are not closed by another header comment. The comment must communicate what the method/function does clearly, and explain important considerations when using the method or function. They must also explain the parameters, returns, and situations it may throw or exit.

#### Typescript
Use JSDoc headers `/** */` in Typescript . Use the `@param`, `@returns`, `@throws`, and other applicable tags.

````
/*
 * Foo method.
 *
 * @param bar The bar parameter.
 * @returns The computed baz.
 * @throws If `bar` is less than 0.
 */
private foo(bar: number) {
  if (bar < 0) {
    throw new Error('bar must be greater or equal to 0.');
  }

  const baz = bar + 1;
  return baz;
}
````

#### C
Use comments similar to the typescript comments with similar fields as the JSDoc ones. Use "Param:" and "Returns:" for @param and @returns. C does not have native exception handling, if a mechanism is used to inform the host environment or print about runtime errors inside the WASM virtual machine, clearly communicate that. Do not use a double asterisk in the opening `/*`.

````
/*
 * Foo function.
 *
 * Param: bar The bar parameter.
 * Returns: The computed baz.
 * 
 * Will print an error if bar is less than 0.
 */
int foo(int bar) {
  if (bar < 0) {
    fprintf(stderr, "bar must be greater or equal to 0.");
  }

  const int baz = bar + 1;
  return baz;
}
````

Method/function comments may also be used in class members or variables when it is important to explain them in detail. We don't use line or non-JSDoc header comments in Typescript because editors often don't pick them up as belonging the class member or variable.

```
// TS
/**
 * Foo bar foo bar foo bar foo bar foo bar
 * foo bar foo bar foo bar foo bar foo bar
 * foo bar foo bar foo bar foo bar foo bar
 */
 private fooBar: number;
```
```
// C
/*
 * Foo bar foo bar foo bar foo bar foo bar
 * foo bar foo bar foo bar foo bar foo bar
 * foo bar foo bar foo bar foo bar foo bar
 */
 int fooBar;
```

### Comment tags
Comments may have a tag before them to categorize what the comment is about. Tags may have some effects on the status of the codebase and build system. They are composed of a short capitalized expression (usually a single word) followed by a colon.

#### TODO:
"TODO:" comments marks things that need to be done in the code.

```
// TODO: Allow the increment amount to be an arbitrary value, not just 1.
private incFoo() {
  this.foo++;
}
```

"TODO:" comments have no effect in the status of the codebase or build system, but may be easily searched to find tasks that are pending.

#### FIXME:
"FIXME:" comments mark known broken parts of the code.

```
// FIXME: foo is not being decremented.
private decFoo() {
  let foo = this.foo;
  foo--;
}
```

"FIXME:" comments create warnings in production builds.

#### HACK:
"HACK:" comments explain about hacks that had to be used for any reason and what the problem is.

```
// HACK: For some reason foo is sometimes NaN, this doesn't cause problems in other places, but bar can never be NaN, so
// we are setting it to 0 in this case.
if (isNaN(this.foo)) {
  this.bar = 0;
} else {
  this.bar = this.foo;
}
```

"HACK:" comments have no effects on the state of the codebase or the build system, but can be searched to find areas of code that could use some improvement or to find common denominators of problems.

#### STUB:
"STUB:" comments mark parts of the code where something that is missing from the code has been replaced by a stub to allow general application functionality during development until that part is added. They should not be used to mark stubs in tests, those are intended to remain as stubs.

```
// STUB: The foo service hasn't been implemented yet. For now we are just using a representative value of 1 for foo.
this.bar = 1;
// this.bar = this.fooService.foo();
```

"STUB:" comments are intended only to replace things during development, no builds should be shipped with stub code. The presence of "STUB:" comments will fail production builds.

#### DEV:
"DEV:" comments mark things that are being actively worked on in this very moment. They mark things that should be removed or changed before anyone else sees the code.

```
// DEV: Tracking foo when interacting with the bar UI.
console.log(this.foo);
```

"DEV:" comments generally shouldn't be committed and can never be merged into main. Their presence will fail production builds and emit warnings in development builds.

#### DANGER:
"DANGER:" comment areas mark areas of the code that should only be modified with caution. These areas may be areas where it is essential to break certain written or unwritten rules, such as doing direct DOM manipulation, or when the code needs to behave in a very specific way that may not be very well understood. "DANGER:" comments are always a header comment that explains the danger and why it is that way, and are closed by a closing header comment stating it is the end of the danger area.

```
/*
 * DANGER: This area manipulates the DOM directly. This is needed since foo isn't part of the Angular application, so we
 * must manipulate the DOM directly to manipulate it.
 */

...

const foo = document.getElementById('foo');

...

 /*
  * END OF DANGER AREA.
  */
```

"DANGER:" comments have no effect in the status of the codebase or build system, but serve as a warning against changing code inside the area without due diligence.

## Placeholders
### Strings
Placeholder strings should be prefixed with "[PH]".

```
public appName = '[PH] HybridBookTool';
```

### Symbols
Symbols for placeholder variables, method names, function names, class names, and other symbols should have either "stub" or "placeholder" in them. Make sure to add "STUB:" or "DEV:" comments when applicable.

```
// STUB: foo will be determined differently when the bar service is implemented.
private fooStub = this.baz;
```
